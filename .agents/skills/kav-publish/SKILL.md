# /kav-publish — readers for every chapter, and where they can go

## 1 · Inventory

List `stories/<slug>/chapters/ch*/`. A chapter is **publishable** when `pages/layout.json` exists and every panel in it has a lettered `panels/pNN-panelK.png` (chapter row Written ✓ in `kickoff-state.md`). Show the author the list: publishable, in progress, not started. Only publishable chapters get readers.

## 2 · Build and link

Decide the output folder with the author. Default: in place, `stories/<slug>/chapters/chNN/pages/`. For a site, a single folder is easier to host: `stories/<slug>/site/` with `chNN/` subfolders, the trailer at the root as `index.html`.

For each publishable chapter in order (make sure `pages/` and `carousel/` are current — `python3 tools/assemble.py chapters/chNN/pages/layout.json` if the lettering changed):

```
python3 tools/build_readers.py --story <slug> --chapters chNN --title "<chapter title>" --out <dir>/chNN \
  --next "<next chapter title>" \
  --next-story-url ../chMM/reader-story.html \
  --next-pages-url ../chMM/reader-comic.html \
  --home-url ../index.html
```

- Links are **relative** so the folder works on any host and from disk.
- Each mode links to the **same mode** of the next chapter. The last chapter omits the `--next*` flags and closes on its last line.
- Every reader links home — the trailer deck (rebuild it with `/kav-trailer` so each chapter slide's Story/Comic pills point at the readers) or a simple index.
- Open the first chapter's story reader and click through to the last to check every link.

## 3 · Hand the work over where it can actually be read

A local reader is a production tool. It cannot be opened on a phone, and it cannot be sent to anyone. Finishing a publish means handing the author something they can read in bed and show to a friend — don't wait for them to discover that `127.0.0.1` doesn't travel.

**In ChatGPT / Codex — ChatGPT Sites.** Once at least one reader is built, offer it:

> Your readers are ready. I can package them into a mobile-friendly ChatGPT Site for private review.

**Deploy only on an explicit yes.** Then:

1. **Package** into a story-local checkout, kept out of the Kav repo's git history:

```
stories/<slug>/site/
  .openai/hosting.json        {"project_id": "<id>", "static": {"directory": "dist"}}
  dist/
    index.html                contents page
    brief.html                the story brief
    chapter-art/chNN.jpg      one representative panel per chapter
    chNN/reader-story.html    swipe reader
    chNN/reader-comic.html    page reader
```

Every path relative, every font, image, stylesheet and script inside the package. Nothing may point at a source tree or a localhost port.

2. **The contents page** carries: the title, a one-sentence premise, a link to the brief and storyboard, and per chapter a representative panel, the number and title, and **both** links — swipe reader and comic reader. Say plainly that it is a work in progress.
3. **Readers:** build every publishable chapter, keep next/previous working in the same mode, link each reader home. Give the author the comic-reader link as well as the story one without being asked.
4. **Mobile is the point:** single column, no horizontal overflow, tappable controls, type that doesn't clip, lazy-loaded art after the first chapter, alt text on every image. **Check at phone width and click through**: home → brief, home → swipe, home → comic, reader → next and previous chapter, reader → home. A build that only works on a desktop is not done.
5. **Deploy** with the `sites-building` and `sites-hosting` skills: register the Site once, keep the `project_id`, deploy **owner-only**, wait for success, and give back the URL as the deliverable. Later updates deploy a new version of the same Site — never a new Site per chapter.
6. **Access is a separate decision, every time.** Deploying privately is not sharing. Sharing with named people, and making it public, are each their own explicit yes. Say so rather than assuming an owner-only deployment is visible to a friend.
7. **Record it** in `kickoff-state.md`:

```
## Publishing
- WIP surface: ChatGPT Sites
- Site URL: https://...
- Site project: registered
- Access: owner-only | shared | public
- Deployed version: <version/date>
- Included chapters: ch01–chNN
- Package path: stories/<slug>/site/dist/
```

Mark the site **stale** whenever a deployed reader, the brief, a chapter title, chapter art or a navigation link changes.

**In Claude** — publish the readers as artifacts and share the links; the interactive review tools stay the better surface for picking. Readers embed their images, and `build_readers.py` prints each file's size: **one artifact holds about 16 MB**, so publish **one artifact per chapter** rather than the whole book in one page, and dial the art back with `--page-px` / `--slide-px` / `--slide-q` if a chapter comes out over. Publish the contents page as its own artifact and link the chapters from it. **Elsewhere** — any static host (below).

The story files are the source of truth on every host. A Site or an artifact is the review handoff, not the book's permanent home.

## 4 · Surfaces — explain, then ask

Every surface is fed by what chapters already produce; none needs new art.

| Surface | What goes | How |
|---|---|---|
| **Any static host** | the readers + trailer folder | it's plain HTML and images — upload the folder anywhere |
| **Netlify** | same folder | drag the folder onto app.netlify.com/drop, or connect a repo |
| **GitHub Pages** | same folder in a repo | push it, enable Pages on the branch/folder |
| **Instagram** | `pages/carousel/NN-*.jpg` per chapter (1080×1350, reading order) and `package/slides/*.png` for the trailer (1080×1920) | post manually as carousels (Instagram carousels cap at 20 items — split long chapters) |
| **PDF / print** | `pages/pNN.png` | not built in yet; the page PNGs are print-shaped. Right-to-left books need reversed page order |

Ask the author, once per story: which surfaces; for a site, where it's hosted and whether it should be a separate repo. Record the answers under Links in `kickoff-state.md`.

## 5 · Closing the book

When the last chapter is published, say so plainly — the book is finished, here is the whole thing in one link — and update `kickoff-state.md`'s Progress to **Done**.

**Report what it cost**, from the story's own ledger:

```
python3 tools/ledger.py --story <slug>
```

Give the figure as what it is: a **documented minimum** — every image Kav generated for this story, rerolls and rejects included. Name what it leaves out (anything made before the ledger existed, failures a provider may still have charged for, rows with no price on record) and say plainly that a provider dashboard covers the whole account and is **not** this book's cost. Keep model spend separate from subscriptions, hosting and time. Then, once and only once per book, offer the feedback pass:

> Kav is new, and we read everything. Five minutes of what worked and what didn't shapes what gets built next. Want to do it now?

On a yes, **interview them** — one or two questions at a time, in the room's language, following up on anything interesting. Don't paste a form:

1. Did you finish the book?
2. Do you like it?
3. How was the process — where did it flow, where did it drag?
4. How happy are you with the result: the story? the visuals?
5. What didn't work?
6. What's your next project?

Write their answers to `stories/<slug>/feedback/<slug>-<date>.md`: Kav version (from `tools/check_setup.py`), provider and models used, chapter and panel counts, the link to the published book, then the questions with their answers **verbatim**. Your own commentary goes in a clearly marked section at the end, or nowhere.

Then offer every delivery route and let them choose:

- **Paste it here** — print the whole file in the chat as one block they can copy and send wherever they like. Always offer this; it works on every host and every device.
- **GitHub** — open an issue at https://github.com/oraboy/kav/issues, or send a pull request if they want to fix something themselves.
- **Email or WhatsApp** — Kav's author reads both; the beta invitation carries the details. Never invent an address or number.

Nothing is sent anywhere by Kav. The file is theirs; they send it.

## Hard rules

- **Never publish, upload, push or post without the author's explicit yes** for that specific action.
- **Deploying privately is not sharing.** Access changes — named people, or public — are each a separate explicit decision.
- Feedback is offered once per book, written down verbatim, and never sent on the author's behalf.
- Never commit `.env` or keys along with a site folder.
- Readers are rebuilt from lettered panels — never hand-edit the generated HTML.
